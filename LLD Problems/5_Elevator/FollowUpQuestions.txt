*   How would you avoid global lock contention in `getElevator()` assignment flow ?

>>  Avoid one globally synchronized assignment path for all elevator requests.
    
    Current bottleneck:
        - All floor requests serialize on ElevatorSystem lock.

    Use optimistic assignment/reservation approach.

    Each elevator maintains:
        - pending request count
        - reserved capacity
        - current movement metadata

    Assignment flow:
        - Take lightweight snapshot of elevators.
        - Select best candidate.
        - Atomically reserve slot in that elevator.
        - If reservation fails, retry with another elevator.

    This reduces global coordination contention significantly.

    Tradeoff:
        - Scheduling uses eventually consistent snapshots.
        - More retry complexity.

*   How would you ensure multiple concurrent floor requests do not repeatedly assign the same elevator ?

>>  Serialize assignment decision or use atomic reservation.

    Without coordination:
        - Multiple threads may observe same elevator snapshot.
        - Delegation strategy may repeatedly assign same elevator.

    Solution:
        - Synchronize assignment flow.
        - OR atomically reserve capacity during delegation.

    This ensures request distribution remains balanced under concurrency.

*   How would you preserve route-aware scheduling while still using BlockingQueue ?

>>  Use BlockingQueue only for wakeup signaling, not request ordering.

    Elevator scheduling depends on:
        - direction
        - future stops
        - path optimization

    FIFO queue alone is insufficient.

    Better approach:
        - SchedulingStrategy still owns request ordering.
        - BlockingQueue acts only as worker notification mechanism.

    Flow:
        - queueRequest() updates scheduler.
        - Signal queue wakes elevator worker.
        - Scheduler decides next optimal floor.

    This preserves scheduling flexibility while simplifying coordination.

*   Why is one worker thread per elevator preferable over multiple worker threads ?

>>  Elevator behaves like a sequential state machine.

    At any instant elevator has:
        - one current floor
        - one direction
        - one movement state

    Multiple worker threads may:
        - produce conflicting movements
        - corrupt state transitions
        - violate scheduling order

    Single worker model:
        - simplifies synchronization
        - preserves deterministic behavior
        - naturally models real elevator movement
